# 术语上下文判断与最终清单来源修复

实际案例：P20在相关研究中写“Transformer[4]、GNN[5]等网络结构”，最终确认清单没有GNN修改。旧结果却列出GNN应改为KNN，以及GNN与CNN/RNN形近的未解决问题。

根因有两处：`audit._name_check_issues`将低频形近术语直接转为错误，不经过语义判断；`review._precheck`再次将形近或章节分布扫描结果转为强制未解决项。最终清单又从所有审查发现反推“没生成补丁就是没完成”，混淆了候选判断与用户确认的修改。

修复内容：

- 删除审查与复核中的词频/形近直接判错路径。词表按文档顺序提供具体位置、章节、所在段落和相邻段落，不展示频次作为判断线索。
- 术语核验要求high confidence、确切段落、逐字可定位的语义证据和依据。缺少上下文、编造引文、理由仍依赖频次或只差字符时丢弃。发现一处错误也只针对该位置，不默认全文替换。
- 提示词明确GNN/KNN/CNN/RNN可为不同对象；不能以出现一次判错，也不能把“CNN一般用于图像”当作其不能处理序列的证据。
- 每条结果未完成项必须关联最终确认的patch_id。取消项、选中但写回失败项保留；未进入确认的审查候选和未定位建议不进入此框。
- 旧任务页面通过读取时过滤兼容；旧报告重新查看/下载时同步更新此节，保留其它历史记录。已下载的旧文件和论文正文不被改写。

测试覆盖：GNN/KNN/CNN/RNN合法共存、低频形近不报错、相同GNN在一段正确而另一段定义为k近邻时只指向后者、无引用/虚构引用拒绝、旧确认恢复不带入旧候选、旧页面和报告过滤，以及已确认项仍能报告未完成。

验收：完整回归385 passed、1 skipped、23 subtests passed；前端构建通过。部署后直接读取实际受影响任务，结果框及报告未完成节均无GNN项，网站健康接口返回ok。验收没有重新运行用户论文的模型审查。

这些检查验证判断流程与输出边界，不代表模型语义判断能达到绝对正确。新语义规则用于之后实际执行的审查；已完成任务不会自动重新调用模型。
